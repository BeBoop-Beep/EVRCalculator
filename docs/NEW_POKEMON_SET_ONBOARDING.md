New Pokémon Set Onboarding Runbook

Purpose

This runbook defines the production-safe process for detecting, registering, scraping, modeling, simulating, and publishing a newly released Pokémon set in EVRCalculator.

It replaces the original Pitch Black notes with the final order proven during onboarding.

The workflow is designed for manual execution today and a resumable automated onboarding pipeline later.

Important architecture constraint

A normal daily scrape cannot discover a completely unknown set. The existing scrape runner begins with sets already registered in the Python constants library and in public.sets as scrape-ready.

New-set detection must therefore run as a separate preflight before the daily scrape batch is created:

TCGplayer discovery
→ onboarding job
→ source configuration PR
→ merge and deploy
→ database registration
→ scrape and market aggregation
→ pull-model completion
→ analytics and simulation
→ public snapshot publication

A newly detected set must never block the normal scrape of existing sets.

Correct manual process

Replace placeholders as follows:

<set-key>       camelCase canonical key, such as pitchBlack
<set-name>      display name, such as Pitch Black
<market-date>   actual market observation date, YYYY-MM-DD
<set-uuid>      public.sets.id
<api-set-id>    Pokémon API set ID, such as me5

1. Detect the set on TCGplayer

Confirm the new Pokémon set is present in the TCGplayer Pokémon catalog and resolve the TCGplayer set ID used by the cards and sealed price-guide endpoints.

Record the TCGplayer set ID, set name, cards endpoint, sealed-products endpoint, and discovery timestamp. Do not rely only on a normalized name.

2. Resolve authoritative Pokémon API metadata

Resolve the same set through the Pokémon TCG API before generating the source configuration.

Require a unique, credible match and collect:

SET_ID

SET_NAME

series / era

RELEASE_DATE

PRINTED_TOTAL

TOTAL

SYMBOL_IMAGE_URL

LOGO_IMAGE_URL

Do not construct image URLs from a guessed URL pattern. Use the values returned by the API.

If the set exists on TCGplayer but not yet in the Pokémon API, stop at awaiting_pokemon_api_metadata and retry later rather than guessing the era or API ID.

3. Generate the targeted set configuration

Create:

backend/constants/tcg/pokemon/<era-folder>/<set-key>.py

Register it in:

backend/constants/tcg/pokemon/<era-folder>/setMap.py

The generated file must include authoritative Pokémon API metadata, validated TCGplayer card and sealed URLs, numeric pull-rate placeholders rather than blank strings, and an explicit pending pull-model state.

Do not run the broad historical bootstrap over every era during daily discovery. New-set automation must update only the targeted set and its era map.

4. Commit the source registration through GitHub

Do not let the production scraper write directly to main.

Use a dedicated automation branch such as:

automation/onboard-pokemon-<set-key>

Run focused configuration validation, then commit, push, open a pull request, auto-merge only after required checks pass, and deploy/pull updated main on the VM.

The production checkout must remain clean and on main.

5. Sync the constants registration into public.sets

Preview:

python backend/scripts/sync_pokemon_eras_and_sets.py

Apply:

python backend/scripts/sync_pokemon_eras_and_sets.py --apply

Verify the new row contains the correct canonical key, Pokémon API set ID, release metadata, TCGplayer URLs, and ready_for_daily_scrape = true.

6. Run the initial TCGplayer scrape

Preview target resolution:

python backend/scripts/run_pokemon_set_scrape.py --set <set-key>

Run:

python backend/scripts/run_pokemon_set_scrape.py --run --set <set-key>

Verify cards, card variants, current prices, and sealed products populated; no empty-string numeric values reached CardDTO; and the scrape report shows one successful target.

7. Generate the first daily Set Value

Set Value is derived from market observations written by the scrape, but it is not generated by the scrape command itself.

Run it immediately after a successful scrape.

Preview:

python backend/scripts/backfill_pokemon_set_value_daily_history.py \
  --set <set-key> \
  --start-date <market-date> \
  --end-date <market-date>

Apply:

python backend/scripts/backfill_pokemon_set_value_daily_history.py \
  --set <set-key> \
  --start-date <market-date> \
  --end-date <market-date> \
  --commit

The market date must be derived from the newest successful price observation. It must not be hardcoded in automation.

Verify pokemon_set_value_daily_history contains a positive standard row. One day is enough to display current Set Value even though movement comparisons remain unavailable.

8. Synchronize Pokémon API card images

Preview:

python backend/scripts/sync_pokemon_images.py --sets "<set-name>"

Apply:

python backend/scripts/sync_pokemon_images.py --sets "<set-name>" --apply

Verify the API returns the complete reported card count, no partial page result is accepted, all expected cards match, card and variant images populate, and the resolved Pokémon API set ID matches the configuration.

Do not run --apply before the preview during manual onboarding.

Automated mode may apply directly only because the image client now has bounded retries, completeness validation, and all-or-nothing writes.

9. Build the rarity census

select
  lower(trim(c.rarity)) as rarity,
  count(distinct c.id) as card_count
from public.cards c
join public.sets s
  on s.id = c.set_id
where s.canonical_key = '<set-key>'
group by lower(trim(c.rarity))
order by lower(trim(c.rarity));

Automatically update the configuration’s common, uncommon, and rare pool counts. These are card-pool counts, not hit-rate denominators.

10. Complete and validate the pull model

Do not run the simulation while required hit-rate values are zero or unknown.

Validate that every raw rarity is classified; every required hit rarity has a positive denominator; reverse and rare slot probabilities are finite, nonnegative, and total 1.0; residuals are nonnegative; pack-level rates are not accidentally doubled or halved; and the product is actually compatible with the selected pack model.

A regular set may use an explicitly approved era template only when its collation is confirmed compatible.

A special Anniversary product must not automatically inherit the normal Mega Evolution pack model.

When incomplete, stop at awaiting_pull_rates and resume after a verified source or approved model is supplied.

If the configuration changed, create a focused pull-model PR, merge it, and deploy updated main before simulation.

11. Build desirability inputs before simulation

Preview:

python backend/scripts/build_pokemon_set_desirability_inputs.py \
  --set <set-key> \
  --log-level INFO

Apply:

python backend/scripts/build_pokemon_set_desirability_inputs.py \
  --set <set-key> \
  --commit \
  --log-level INFO

Verify the current authoritative hit-policy version was used and that the current component row has valid coverage.

This first pass supplies roster/Collector Appeal inputs available before the first simulation.

12. Run the simulation

Confirm selection:

python backend/scripts/run_all_v2_sets.py \
  --set "<set-name>" \
  --dry-run

Run:

python backend/scripts/run_all_v2_sets.py \
  --set "<set-name>"

Verify exactly one set was selected, the run completed, all expected simulation detail tables populated, pull rates are valid, and no rarity or slot mapping is incomplete.

13. Rebuild desirability after simulation

python backend/scripts/build_pokemon_set_desirability_inputs.py \
  --set <set-key> \
  --commit \
  --log-level INFO

This second pass is required because Opening Desirability / CA7 uses simulation-derived market and opening inputs that do not exist before the first simulation.

Verify Collector Appeal, Chase Appeal where required, Opening Desirability, and canonical CA7 are available; the current simulation run is linked; and Overall RIP is no longer missing opening_desirability_ca7.

14. Build coordinated market snapshots

python backend/scripts/build_pokemon_set_market_snapshots.py \
  --set-id <set-key> \
  --commit \
  --days 365 \
  --window 365d

Verify Set Value, the current OPvC point, Top Chase, Cards data, and source dates.

15. Rebuild global Explore rankings

python backend/scripts/build_pokemon_explore_rankings_snapshot.py \
  --all \
  --commit

A new set changes the ranking cohort, so this remains an all-set rebuild.

16. Build the targeted set-page snapshot

python backend/scripts/build_pokemon_set_page_snapshots.py \
  --set-id <set-key> \
  --commit

Build this after global Explore rankings so the set page receives the canonical current public RIP contract.

Every step must be idempotent and resumable.

Scheduling

Run discovery before daily scrape-batch creation. Discovery or onboarding failure must not prevent existing known sets from scraping.

new-set discovery preflight
→ create/resume onboarding jobs
→ continue normal daily scrape for known sets

Run the onboarding worker separately so it can resume after PR merges, deployments, provider availability, or pull-rate approval.

Git safety

Never commit from the production main checkout. Use a separate worktree or automation clone.

Auto-merge is allowed only when the set match is unambiguous, generated config validation passes, focused tests pass, required CI passes, and no unrelated files changed.

Performance rules

Automated --commit mode should not run every expensive child command twice.

Use one whole-pipeline --dry-run preview and one guarded --commit execution. Keep the one-set simulation selection dry run because it is inexpensive. Use targeted operations everywhere except Explore rankings, which must remain --all.

Non-negotiable safety gate

The pipeline may fully automate discovery, metadata, configuration, scraping, Set Value, images, rarity census, desirability, simulation, and publication only when a valid pull model is available.

It must never fabricate hit rates or treat zero placeholders as simulation-ready.
